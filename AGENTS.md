## Operating Rules

These rules are permanent and non-negotiable. They do not change as the project evolves.

### Architecture boundaries

- Every domain feature lives in its own `internal/module/{name}/` package — a fully self-contained vertical slice
- Modules are **never** imported by other modules; cross-module dependencies are expressed as interfaces and bridged by adapters
- `internal/platform/` is shared infrastructure only — it contains no business logic
- All module wiring happens in `cmd/api/main.go` and nowhere else

### Layer responsibilities

- **Handlers** bind requests and map errors to HTTP responses — no business logic, ever
- **Services** own all business rules — they depend on repository interfaces, not concrete types
- **Repositories** define their own port interfaces in `repository.go` and implement them in `repository_sqlc.go`
- **`pkg/dbsqlc/`** is the only code that touches the DB driver — never bypassed, never edited by hand

### SQL rules

- All SQL lives in `db/query/*.sql` — never write inline SQL strings in Go
- `pkg/dbsqlc/` is generated by `sqlc generate` — run it after any change to `db/query/` or `db/schema.sql`, never edit it directly
- `db/schema.sql` must stay in sync with the cumulative state of all migrations
- Never modify an already-applied migration — create a new numbered one instead

### Compile-first rule

Always in this order — never skip, never reverse:

```bash
go build ./...       # must pass before anything else
go vet ./...
go test -race ./...
```

### Cross-module communication

When module A needs data from module B:
1. Module A defines the interface it needs in its own `repository.go`
2. An adapter in `A/adapters/` implements that interface using B's concrete repository
3. Wiring happens only in `cmd/api/main.go`

---

## Hard Rules

1. All SQL in `db/query/*.sql` — no inline SQL in Go
2. Never edit `pkg/dbsqlc/` — regenerate with `make sqlc`
3. Handlers never contain business logic
4. Never call the DB from a handler — always handler → service → repository
5. Never import `internal/module/X` from `internal/module/Y`
6. Never modify an applied migration
7. Keep `db/schema.sql` in sync with migrations
8. Always `go build ./...` before `go test`
9. Always test with `-race`
10. Never commit stale generated code

## Documentation Synchronization

When changing architecture, module responsibilities, workflows, or dependency boundaries:

- Update the affected file under `docs/`
- Keep `docs/architecture.md` aligned with the current folder structure and dependency graph
- Keep `docs/modules.md` aligned with each module's actual responsibilities and status
- Keep `docs/workflows.md` aligned with actual commands and tooling
- Remove stale examples and outdated module references
- Record non-obvious decisions and discoveries in `docs/ai-learnings.md`
- Treat documentation drift as a bug
